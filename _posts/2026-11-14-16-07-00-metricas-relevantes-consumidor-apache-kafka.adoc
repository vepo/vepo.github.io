No meu trabalho de mestrado, precisei analisar a fundo diversas métricas dos clientes Apache Kafka para criar um mecanismo auto-adaptativo para ele. Neste post, quero detalhar algumas métricas e como elas se relacionam com alguns parâmetros.

O ecossistema Apache Kafka é composto por Broker, Produtor, Consumidor, Kafka Streams e Kafka Connect (com seus connectors). Quero começar pelo Consumidor. Todas as métricas do Kafka estão documentadas na página https://kafka.apache.org/44/operations/monitoring/[Monitoring] (Monitoramento) da documentação do Kafka. Essa página é organizada por componente e eu sempre recomendo a leitura, pois novas métricas são adicionadas a cada nova versão.

Para entender as métricas, precisamos primeiro entender como funciona um consumidor Kafka.

== Como funciona o consumidor Kafka?

_Caso queira assistir a uma aula que dei há 2 anos sobre isso, recomendo o vídeo https://youtu.be/bZ8wf9MKPH4[Apache Kafka do Zero! (iii) Como receber mensagens?]._

{% youtube bZ8wf9MKPH4 %}

O consumidor Kafka funciona de forma assíncrona. O código que instancia e processa as mensagens usa a thread da aplicação, e o consumidor mantém uma thread de rede para se comunicar com o broker. A ideia é que as duas threads funcionem independentemente, sem que sejam bloqueadas, e se comuniquem por meio de buffers.

Para descrever como o consumidor funciona, vou usar o exemplo abaixo. Removi toda a lógica de processamento e deixei basicamente a interação com o consumidor.

[source,java]
----
Properties properties = new Properties();
properties.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");  // Obrigatório
properties.put(ConsumerConfig.GROUP_ID_CONFIG, "meu-primeiro-consumidor");  // Obrigatório
properties.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, GeolocationDeserializer.class);   // Obrigatório
properties.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, WeatherInfoDeserializer.class); // Obrigatório
properties.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG, 100);  // Opcional, valor padrão 500
KafkaConsumer consumidor = new KafkaConsumer<>(properties);
consumidor.subscribe(Arrays.asList("weather"));
while (running.get()) {
    consumidor.poll(Duration.ofSeconds(1))
              .forEach(this::processaMensagem);
}
----

O método `poll` é central no entendimento do consumidor Kafka. Para esse método ser chamado, é necessário ter um consumidor iniciado e com algumas partições atribuídas. No exemplo, as partições são atribuídas automaticamente, uma vez que usamos o método `subscribe`, mas elas podem ser atribuídas manualmente se usarmos os métodos `assign`. Só faça isso manualmente se você souber exatamente o que está fazendo!!! Confie no algoritmo de atribuição automática ou, se quiser, implemente um usando o parâmetro https://kafka.apache.org/44/configuration/consumer-configs/#consumerconfigs_partition.assignment.strategy[`partition.assignment.strategy`].

Toda vez que a thread de aplicação chama o método `.poll(Duration.ofSeconds(1))`, ela fica bloqueada até que uma das condições ocorra: o timeout de `Duration.ofSeconds(1)` seja atingido ou existam registros disponíveis para retorno, respeitando o limite de https://kafka.apache.org/44/configuration/consumer-configs/#consumerconfigs_max.poll.records[`max.poll.records`]. O `max.poll.records` é um limite superior; o `poll` não precisa retornar exatamente essa quantidade e pode retornar uma lista vazia. Enquanto não houver registros disponíveis, o cliente mantém a comunicação com o broker e o buffer de busca; quando há registros, o `poll` os retorna para processamento. O cliente Kafka também mantém um mecanismo de prefetch: ele pode buscar registros antecipadamente para que a próxima chamada de `poll` já encontre dados no buffer. Isso reduz o impacto das idas ao broker.

image::artigos/kafka/consumer-poll.png[]

O cenário ideal é que o `poll` nunca bloqueie a thread de processamento por muito tempo.

Uma operação de `Fetch` é enviada para um broker específico e pode incluir várias partições hospedadas nesse broker. Quando iniciamos um consumidor Kafka usando a configuração https://kafka.apache.org/44/configuration/consumer-configs/#consumerconfigs_bootstrap.servers[`bootstrap.servers`], deve haver ao menos um broker do cluster listado. Isso não significa que o consumidor se comunicará apenas com esse broker; ele pode se comunicar com qualquer broker, dependendo das partições que estiver consumindo. A lista completa de brokers pode não ser conhecida inicialmente, mas, ao se conectar, o cliente descobre quais brokers existem e quais deve contatar.

Uma requisição `Fetch` pode buscar dados de várias partições do mesmo broker. Quando a aplicação precisa escalar, o paralelismo é limitado pelo número de partições: mais threads ou consumidores do que partições ficarão ociosos.

Para resolver esse problema, algumas pessoas tentam compartilhar um consumidor entre diversas threads de processamento. Eu não recomendo essa abordagem!! Por quê? Porque o `KafkaConsumer` não é thread-safe e o processamento de mensagens é sequencial dentro de uma partição. O commit do offset, manual ou automático, também é sequencial e pertence à partição, não à mensagem. No Kafka, não commitamos uma mensagem; commitamos a posição/offset de uma partição.

Por exemplo, observe a distribuição de mensagens no tópico `weather` abaixo. A partição 0 possui 6 mensagens, a partição 1 possui 4 e a partição 2 possui 5 mensagens. Se eu tenho mais de uma thread de processamento consumindo a partição 0 e o processamento da mensagem 3 falha, mas o processamento da mensagem 4 é feito com sucesso, o commit será feito depois da mensagem 4. Isso significa que, se a thread reiniciar, ela começará a consumir a partir da mensagem 5. Mesmo que a mensagem 3 não seja comitada, o commit não é da mensagem, mas do offset da partição; ao commitar o offset 5, as mensagens anteriores naquela partição são consideradas processadas.

.Descrição da distribuição de mensagens em um tópico `weather` com 3 partições e 15 mensagens.
image::artigos/kafka/consumer-offsets.png[]

É possível ter várias threads processando registros, mas não compartilhando o mesmo `KafkaConsumer`. A distribuição de partições entre consumidores do mesmo grupo é feita pelo próprio Kafka; cada consumidor deve ser usado por uma única thread.

Outra característica importante do consumidor é o mecanismo de `heartbeat`, que faz com que o grupo de consumidores perceba se um membro está ativo. O consumidor mantém uma thread de heartbeat em segundo plano. Se o broker não receber heartbeats dentro de https://kafka.apache.org/44/configuration/consumer-configs/#consumerconfigs_session.timeout.ms[`session.timeout.ms`], o membro é removido do grupo e uma operação de rebalance é chamada para distribuir as partições desse membro entre os outros consumidores. Além disso, se a thread de aplicação ficar sem chamar `poll` por mais que https://kafka.apache.org/44/configuration/consumer-configs/#consumerconfigs_max.poll.interval.ms[`max.poll.interval.ms`], o consumidor também é considerado inativo e sai do grupo.

É importante que o tempo entre chamadas de `poll` — incluindo o processamento do lote retornado — seja bem menor que `max.poll.interval.ms`, e que a thread de processamento nunca pare de executar o `poll` por longos períodos. Caso exista alguma indisponibilidade, a aplicação deve se precaver e chamar os métodos https://kafka.apache.org/42/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html#pause(java.util.Collection)[`pause`] e https://kafka.apache.org/42/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html#resume(java.util.Collection)[`resume`]. Em muitos casos de uso, é necessário controlar o consumo de algumas partições, caso elas sejam distribuídas para clusters específicos.

Agora que já entendemos o funcionamento do consumidor, vamos ver as métricas relevantes para entendermos a saúde dele?

== Métricas relevantes

Para entender as métricas, vou separá-las por operações: consumo e distribuição de carga.

Todas as métricas do Kafka são expostas pela biblioteca Kafka usando JMX. Elas podem ser consultadas via JMX ou usando exportadores como o https://github.com/prometheus/jmx_exporter[Prometheus JMX Exporter].

=== Métricas de consumo

https://kafka.apache.org/44/operations/monitoring/#consumer-fetch-metrics[Métricas do Fetch]

==== _Lag_, ou o atraso do consumidor

A primeira é o _lag_. Lag é o atraso do consumidor em relação ao final de uma partição, ou seja, a distância entre a última mensagem consumida e a última mensagem produzida na partição. O consumidor expõe essa métrica de quatro formas e em dois contextos, conforme descrito abaixo.

.Métricas de lag do consumidor Kafka. As métricas são agrupadas por contexto (cliente e partição) e expostas via JMX.
[cols="1,1,3,4",options="header"]
|===
| Métrica
| Contexto
| Descrição
| MBean

| `records-lag-max`
| Cliente
| Maior lag entre as partições atribuídas ao cliente. É útil para alertas e para uma visão global do atraso.
| `kafka.consumer:type=consumer-fetch-manager-metrics,client-id="{client-id}"`

| `records-lag`
| Partição
| Lag atual da partição: diferença entre o último offset produzido e a posição atual do consumidor na partição.
| `kafka.consumer:type=consumer-fetch-manager-metrics,partition="{partition}",topic="{topic}",client-id="{client-id}"`

| `records-lag-avg`
| Partição
| Média do lag da partição na janela de amostragem; suaviza variações pontuais.
| `kafka.consumer:type=consumer-fetch-manager-metrics,partition="{partition}",topic="{topic}",client-id="{client-id}"`

| `records-lag-max`
| Partição
| Maior lag observado para a partição na janela de amostragem; ajuda a identificar picos.
| `kafka.consumer:type=consumer-fetch-manager-metrics,partition="{partition}",topic="{topic}",client-id="{client-id}"`
|===

O lag é medido em número de registros (offsets), não em tempo; ele não representa o atraso temporal de uma mensagem.

Se o _lag_ é crescente, significa que a vazão (_throughput_) de processamento do seu consumidor não é suficiente, o que pode indicar a necessidade de mais threads de processamento, mas essas são limitadas pelo número de partições. Se o número de consumidores já é igual ao número de partições, será necessário encontrar um conjunto melhor de configurações que permita aumentar a vazão desses consumidores.

É importante ressaltar que o _lag_ não é o atraso de uma mensagem. No Kafka, o timestamp de uma mensagem é definido pela aplicação que a produz; isso significa que não há uma ordenação temporal dentro de uma partição, mas uma ordenação lógica. A partição é ordenada conforme a entrega da mensagem, e o lag não mede o atraso temporal de uma mensagem específica.

É aceitável que o _lag_ cresça? Sim. É possível que uma aplicação tenha uma vazão sustentável mesmo que o _lag_ cresça em alguns momentos do dia. Isso depende das características do sistema e da necessidade de consumo da mensagem. Há aplicações cujo uso varia durante o dia, com picos e momentos de baixa. Se o processamento não é urgente, é possível que o _lag_ acumulado nos momentos de pico seja consumido nos momentos de baixa. Acompanhar o _lag_ é importante para se entender o comportamento da aplicação.

==== Taxa de consumo, ou vazão (_throughput_)

A taxa de consumo em um consumidor Kafka pode ser expressa tanto em bytes quanto em mensagens. Essas duas métricas também podem ser relacionadas para se extrair o tamanho médio das mensagens consumidas. A métrica é exposta tanto por cliente quanto por tópico, quando um mesmo consumidor é usado para consumir diversos tópicos.

.Métricas de vazão de consumo do consumidor Kafka. As métricas são agrupadas por contexto (cliente e tópico) e expostas via JMX.
[cols="1,1,3,4",options="header"]
|===
| Métrica
| Contexto
| Descrição
| MBean

| `bytes-consumed-rate`
| Cliente
| Taxa média de bytes consumidos por segundo pelo cliente.
| `kafka.consumer:type=consumer-fetch-manager-metrics,client-id="{client-id}"`

| `records-consumed-rate`
| Cliente
| Taxa média de registros (mensagens) consumidos por segundo pelo cliente.
| `kafka.consumer:type=consumer-fetch-manager-metrics,client-id="{client-id}"`

| `bytes-consumed-rate`
| Tópico
| Taxa média de bytes consumidos por segundo para o tópico, no contexto do cliente.
| `kafka.consumer:type=consumer-fetch-manager-metrics,client-id="{client-id}",topic="{topic}"`

| `records-consumed-rate`
| Tópico
| Taxa média de registros (mensagens) consumidos por segundo para o tópico, no contexto do cliente.
| `kafka.consumer:type=consumer-fetch-manager-metrics,client-id="{client-id}",topic="{topic}"`
|===

As métricas por tópico permitem comparar a vazão entre tópicos consumidos pelo mesmo cliente. A razão entre `bytes-consumed-rate` e `records-consumed-rate` pode ser usada para estimar o tamanho médio dos registros consumidos.

A vazão é a velocidade de processamento e pode ser comparada com a velocidade de produção de mensagens. Logicamente, toda mensagem produzida deve ser consumida em algum momento; quando a velocidade de produção é superior à velocidade de consumo, o _lag_ tende a aumentar.

=== Métricas de Processamento

==== Tempo médio de processamento

O processamento é sempre realizado entre chamadas ao método `poll`, que deve ser chamado constantemente. O `poll` retorna uma lista de mensagens — que pode ser vazia — e não uma única mensagem. Por isso, o tempo médio de processamento de uma mensagem deve ser calculado pela aplicação; o consumidor calcula apenas o tempo médio entre chamadas de `poll`.

.Métricas de tempo entre chamadas de `poll` do consumidor Kafka. As métricas são expostas no contexto do cliente via JMX e ajudam a identificar intervalos longos sem `poll`.
[cols="1,1,3,4",options="header"]
|===
| Métrica
| Contexto
| Descrição
| MBean

| `time-between-poll-avg`
| Cliente
| Tempo médio entre as chamadas de `poll`.
| `kafka.consumer:type=consumer-metrics,client-id="{client-id}"`

| `time-between-poll-max`
| Cliente
| Tempo máximo entre as chamadas de `poll`.
| `kafka.consumer:type=consumer-metrics,client-id="{client-id}"`

| `last-poll-seconds-ago`
| Cliente
| Tempo, em segundos, desde a última chamada de `poll`.
| `kafka.consumer:type=consumer-metrics,client-id="{client-id}"`
|===

Essa métrica é importante de ser monitorada, pois, caso algum consumidor tenha um tempo entre chamadas ao `poll` maior que https://kafka.apache.org/44/configuration/consumer-configs/#consumerconfigs_max.poll.interval.ms[`max.poll.interval.ms`], uma operação de rebalance será iniciada, o que pode reduzir a vazão.

==== Número médio de mensagens no `poll`

O Kafka Consumer não possui uma métrica que diga quantas mensagens retornam em cada chamada ao método `poll`. Essa métrica pode ser criada pela aplicação. Se você olhar a documentação, até encontrará a métrica `poll-records-avg`, mas ela é calculada pelo Kafka Streams e não está disponível no consumidor.

Porém, podemos analisar quantos registros são retornados pelas requisições de `Fetch`. Lembre-se de que o `poll` retorna quando há registros disponíveis, até o limite de https://kafka.apache.org/44/configuration/consumer-configs/#consumerconfigs_max.poll.records[`max.poll.records`], ou quando o timeout fornecido via código expira. A chamada `poll` pode disparar assincronamente requisições de `Fetch` para dispor de mensagens na próxima chamada ao `poll`. Por isso, a métrica `records-per-request-avg` fornece uma informação importante: ela indica a eficácia média das requisições de `Fetch`.

.Métricas de registros por requisição de `Fetch` do consumidor Kafka. A métrica é exposta no contexto do cliente via JMX e indica a eficácia média das requisições de `Fetch`.
[cols="1,1,3,4",options="header"]
|===
| Métrica
| Contexto
| Descrição
| MBean

| `records-per-request-avg`
| Cliente
| Média de registros retornados por requisição de `Fetch` concluída.
| `kafka.consumer:type=consumer-fetch-manager-metrics,client-id="{client-id}"`
|===

Caso a operação de `Fetch` não esteja sendo eficaz, os parâmetros de `Fetch` podem ser alterados para reduzir o tempo de bloqueio do `poll`, fazendo com que as threads de processamento e de rede atuem coordenadamente. Exemplos de parâmetros que podem ser avaliados incluem `fetch.min.bytes`, `fetch.max.wait.ms`, `max.poll.records` e `max.partition.fetch.bytes`.

=== Métricas de Coordenação

As métricas de coordenação cobrem o gerenciamento do grupo de consumidores: heartbeat, _rebalance_ e commit de offset. Elas ajudam a diagnosticar instabilidade do grupo e a correlacionar pausas no processamento com variações de lag e de vazão.

== Conclusão

Neste post, vimos que o consumidor Kafka expõe um conjunto rico de métricas, organizadas por contexto (cliente, partição, tópico e nó) e agrupadas em MBeans distintos via JMX. Cada grupo responde a uma pergunta diferente: o _lag_ diz se o consumidor está atrasado; a vazão diz a que velocidade ele processa; o tempo entre chamadas de `poll` diz se a thread de processamento está progredindo; as métricas de `Fetch` e de rede dizem se a comunicação com o broker está eficiente; e as métricas de coordenação dizem se o grupo está estável.

A ideia central é que nenhuma métrica isolada conta a história completa. Um _lag_ crescente pode ser causado por processamento lento, por `Fetch` ineficaz, por rebalances frequentes ou por limitação de partições. Por isso, o diagnóstico depende de correlacionar métricas de grupos diferentes, e é justamente essa correlação que serve de base para um mecanismo auto-adaptativo, como o que desenvolvi no mestrado. Ao perceber, por exemplo, que o `time-between-poll-avg` se aproxima de `max.poll.interval.ms` enquanto o `records-per-request-avg` permanece baixo, você pode ajustar `max.poll.records` ou `fetch.min.bytes` para reduzir as operaćões de rebalancing.

Para quem está começando a monitorar consumidores Kafka, a recomendação é priorizar o _lag_ e a vazão como painéis principais, e usar as métricas de processamento, rede e coordenação como ferramentas de diagnóstico quando algo sair do esperado. E lembre-se: as métricas evoluem a cada versão do Kafka, então vale revisitar periodicamente a página de https://kafka.apache.org/44/operations/monitoring/[Monitoring] da documentação oficial.
